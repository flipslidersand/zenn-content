先週のClaude Code使用量を集計したら、1週間で1.36Bトークンという数字が出た。

13億トークン。

「さすがに使いすぎでは？」と思って内訳を調べてみると、予想とはかなり違う構造をしていた。

## 内訳を見たら97%がキャッシュだった

Claude Codeのセッションログから、週単位のトークン使用量を集計した結果がこれだ。

| 種別 | トークン数 | 割合 |
|------|-----------|------|
| input | 0.1M | 0.0% |
| cache_create | 30.2M | 2.2% |
| cache_read | 1,326.5M | 97.4% |
| output | 5.9M | 0.4% |
| **合計** | **1,362.7M** | 100% |

1.36Bのうち、1.33B、つまり97.4%がcache_readだった。

一方で、新しくキャッシュに投入されたcache_createは30.2M、Claudeが生成したoutputは5.9M。

単純に合計すると、新しく生成・投入されたトークン量は約36Mになる。

総トークン数だけを見ると1.36Bだが、その大半は過去に処理した文脈の再利用だった。

## cache_readとは何か

ClaudeのAPIには、Prompt Cachingという仕組みがある。

Claude Codeでは、コーディング中に大量の文脈を繰り返し参照する。

たとえば、

- CLAUDE.mdなどのプロジェクト指示
- 読み込んだソースコード
- ツールの情報
- それまでの会話履歴
- セッション内で蓄積したコンテキスト

といったものだ。

毎回すべてを通常のinputとして処理するのではなく、再利用できる部分をキャッシュし、その後のリクエストではキャッシュから読み込む。

ログ上ではこれがcache_readとして現れる。

Prompt Cachingでは通常のinputよりcache_readの単価が低いため、同じ長い文脈を何度も参照するワークロードでは大きな効果がある。

Claude Codeとの相性がかなりいい仕組みだ。

## 1週間で13,972ターン

もう一つ面白かった数字がある。

同じ期間のターン数は、

**13,972ターン**

だった。

7日間で割ると、1日あたり約2,000ターン。

もちろん、これは人間が2,000回チャットを入力したという意味ではない。

Claude Codeでは、

- ファイルを読む
- コマンドを実行する
- 結果を確認する
- コードを書く
- テストする
- 次の判断をする

といった一連のエージェント動作でもモデル呼び出しが発生する。

そのため、人間から見ると「1回お願いしただけ」でも、裏側では複数ターン進む。

13,972ターンという数字は、Claude Codeをチャットというより、常時動いている開発エージェントとして使っていることをよく表している。

## 1ターンあたり約97,000トークン

総トークン数1,362.7Mを13,972ターンで割ると、

**1ターンあたり約97,500トークン**

になる。

かなり大きい。

ただし、その97,000トークンを毎回ゼロから処理しているわけではない。

97.4%はcache_readなので、実際には巨大な文脈を何度もキャッシュから参照しながら、少量の新しい情報を追加して処理している。

この構造を見ると、Claude Codeの動き方がかなり分かりやすい。

## 入出力比は約230:1

さらに面白いのが、Claudeが「読む量」と「書く量」の差だ。

input系を合計すると、input + cache_create + cache_readで約1,356M。

それに対してoutputは5.9M。

つまり、

**入力 : 出力 ≒ 230 : 1**

になる。

Claudeは、自分が出力する量の約230倍の情報を読んでいる。

実際の使用感ともかなり一致する。

Claude Codeは大量のコードや会話履歴を読み込み、

「この3行を直す」「この関数を追加する」「このテストを実行する」

といった比較的小さな出力を返す。

人間に例えるなら、大量の資料を読んで、数行だけ判断を書く仕事に近い。

生成量だけ見ていると、この構造は見えない。

## cache_readが多いのは良いことなのか

少なくともコスト効率という意味では良い状態だ。

同じコンテキストを通常inputとして何度も処理するより、キャッシュから再利用できた方が安い。

今回のログでは97%以上がcache_readだったので、かなり高い割合で既存コンテキストを再利用できている。

逆に、長いセッションなのにcache_readが少なく、通常inputやcache_createが大量に増えているなら、

- キャッシュがうまく効いていない
- コンテキストが頻繁に変化している
- セッションを細かく作り直している

といった可能性を疑ってもいい。

ただし、ここで一つ注意がある。

キャッシュ効率が高いことと、長時間セッションで回答品質が落ちないことは別問題だ。

長い文脈を安く読み直せたとしても、文脈そのものが巨大になれば、重要な情報を取り違えたり、以前決めたルールから徐々にズレたりすることはある。

コスト上の効率と、推論品質上の効率は別に考えた方がいい。

## Max planなので直接の従量課金ではない

今回のClaude CodeはMax planで利用しているため、APIのようにトークン数がそのまま請求額になるわけではない。

ただし、このログを見るとClaude Code内部でどのようにモデルを使っているかはかなり見えてくる。

重要なのは、

**1.36Bトークンすべてが、新しく処理された1.36Bトークンではない**

ということだ。

約97%は既存コンテキストのキャッシュ読み込みだった。

そのため、「総トークン数」だけを見て負荷や利用量を判断すると、実態をかなり誤解する。

API利用の場合も、通常input、cache_write/cache_create、cache_read、outputでは料金体系が異なるため、合計トークン数だけではコストを判断できない。

## まとめ

今回の1週間のClaude Code利用ログは、

- 総トークン数：1.36B
- cache_read：1.33B（97.4%）
- cache_create：30.2M
- output：5.9M
- ターン数：13,972
- 1ターン平均：約97,500トークン
- 入力 : 出力：約230 : 1

という結果だった。

最初に1.36Bという数字を見たときは、とんでもない量を消費しているように見えた。

でも内訳を見ると、そのほとんどは同じ巨大なコンテキストを再利用しているcache_readだった。

Claude Codeの利用量を見るときは、「何トークン使ったか」だけではなく、「そのトークンが何だったのか」まで見る。ここまで見ると、Claude Codeというツールがどう動いているのかもかなり見えてくる。

そして個人的には、1.36Bトークンよりも、

**1週間で13,972ターン回していた**

という事実の方がちょっと怖い。
